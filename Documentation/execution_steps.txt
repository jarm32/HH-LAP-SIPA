PASOS DURANTE Y DESPUÉS DE LA EJECUCIÓN FINAL SECUENCIAL
===========================================================

Contexto actualizado
--------------------

La ejecución final se lanza SIN paralelización, en un único proceso secuencial:

- Un solo run_general.py activo.
- Todos los algoritmos se ejecutan uno detrás de otro.
- Todos los resultados van a una única carpeta:

  results/final_sequential/

Estructura esperada:

results/final_sequential/
├── checkpoints/
├── logs/
├── pareto/
├── statistics/
└── assignments/   # se puede crear, pero estará vacía si no se usa --save_assignments

La carpeta de hipervolumen se generará al final:

results/final_sequential/hypervolume/


Tiempos actualizados por ejecución
----------------------------------

200  -> 300 s  = 5 min
400  -> 450 s  = 7.5 min
600  -> 450 s  = 7.5 min
800  -> 600 s  = 10 min
1000 -> 600 s  = 10 min


Tiempo aproximado por algoritmo
-------------------------------

Cada tamaño tiene 4 instancias × 30 runs = 120 ejecuciones.

200:  120 × 5 min   = 600 min  = 10 h
400:  120 × 7.5 min = 900 min  = 15 h
600:  120 × 7.5 min = 900 min  = 15 h
800:  120 × 10 min  = 1200 min = 20 h
1000: 120 × 10 min  = 1200 min = 20 h

Total por algoritmo:

10 + 15 + 15 + 20 + 20 = 80 h aprox.

Total de toda la batería secuencial:

80 h × 5 algoritmos = 400 h ≈ 16.7 días


Orden esperado de ejecución
---------------------------

run_general.py recorre primero los algoritmos en el orden indicado:

1. random
2. nsga3
3. grasp
4. hh_lap_v0
5. hh_lap_v1

Para cada algoritmo recorre las 20 instancias y 30 runs por instancia.

Cada algoritmo tendrá:

20 instancias × 30 runs = 600 ejecuciones

Total:

5 algoritmos × 600 = 3000 ejecuciones


ANTES DE LANZAR
===============

1. Entrar al proyecto y activar entorno
--------------------------------------

cd /home/gti/jose_antonio_sipa_experiments/code
source ../venv/bin/activate


2. Confirmar que no queda nada ejecutándose
------------------------------------------

ps aux | grep "run_general.py"

Correcto si solo aparece la línea del propio grep.


3. Confirmar tiempos en run_general.py
-------------------------------------

Abrir:

nano run_general.py

Comprobar que TIME_LIMITS_SECONDS está así:

TIME_LIMITS_SECONDS = {
    200: 300,     # 5 min
    400: 450,     # 7.5 min
    600: 450,     # 7.5 min
    800: 600,     # 10 min
    1000: 600,    # 10 min
}


4. Dry run final
----------------

python run_general.py \
  --dry_run \
  --runs 1 \
  --algorithms random nsga3 grasp hh_lap_v0 hh_lap_v1 \
  --results_dir results/final_sequential

Debe mostrar:

Número de instancias encontradas: 20
Total de jobs con --runs 1: 100

También comprobar que los tiempos impresos son:

200  -> 300s
400  -> 450s
600  -> 450s
800  -> 600s
1000 -> 600s


LANZAMIENTO FINAL SECUENCIAL
============================

Lanzar desde:

cd /home/gti/jose_antonio_sipa_experiments/code
source ../venv/bin/activate

Comando final:

nohup python run_general.py \
  --runs 30 \
  --algorithms random nsga3 grasp hh_lap_v0 hh_lap_v1 \
  --results_dir results/final_sequential \
  --resume \
  > ../results/logs/final_sequential.out 2>&1 &

Después comprobar:

ps aux | grep "run_general.py"
free -h
tail -n 40 ../results/final_sequential/logs/run_general.log

Correcto si:
- aparece un único proceso python run_general.py;
- no hay uso de swap;
- el log muestra START del primer job.

CÓMO APROVECHAR RESULTADOS MIENTRAS SE REDACTA EL PAPER
=======================================================

La ejecución es secuencial por algoritmo. Por tanto, conforme termine un algoritmo completo, se pueden empezar a revisar sus resultados parciales.

Ejemplo:
Cuando random tenga 600 checkpoints, random está completo:

find ../results/final_sequential/checkpoints -type f -name "random__*.done" | wc -l

Si devuelve 600, entonces se pueden usar los resultados de random para análisis preliminar.

IMPORTANTE:
Para conclusiones comparativas definitivas entre algoritmos, conviene esperar a que estén todos, porque el hipervolumen comparativo necesita los frentes de todos los algoritmos para cada instancia.

Pero sí se puede ir redactando durante la ejecución:
- metodología experimental;
- configuración de instancias;
- tiempos de ejecución;
- descripción de métricas;
- estructura de almacenamiento;
- explicación de checkpoints y reproducibilidad;
- resultados descriptivos de algoritmos ya terminados;
- tablas internas preliminares por algoritmo ya completo.

Evitar cerrar conclusiones comparativas fuertes hasta tener todos los algoritmos.

Nota: si el CSV tiene cabecera, conviene analizarlo luego con Python/R/pandas para filtrar correctamente.


4. Qué se puede redactar con un algoritmo terminado
--------------------------------------------------

Con un algoritmo terminado puedes ir comentando:
- número de ejecuciones completadas;
- tamaños de Pareto obtenidos;
- estabilidad general de las ejecuciones;
- si hubo errores o no;
- tiempo real aproximado;
- comportamiento individual del algoritmo.

Pero no cerrar aún:
- ranking final entre algoritmos;
- hipervolumen comparativo definitivo;
- dominancia global;
- conclusiones finales de superioridad.

SI LA EJECUCIÓN SE PARA ANTES DE TERMINAR
=========================================

No borrar resultados.

Volver a lanzar el mismo comando con --resume:

cd /home/gti/jose_antonio_sipa_experiments/code
source ../venv/bin/activate

nohup env OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 \
python run_general.py \
  --runs 30 \
  --algorithms random nsga3 grasp hh_lap_v0 hh_lap_v1 \
  --results_dir results/final_sequential \
  --resume \
  > ../results/logs/final_sequential.out 2>&1 &

El script saltará las ejecuciones que ya tengan checkpoint .done.


SI QUIERES PARAR MANUALMENTE
============================

1. Ver proceso:

ps aux | grep "run_general.py"

2. Parar proceso:

pkill -f "python run_general.py"

3. Confirmar:

ps aux | grep "run_general.py"

4. Si se quiere reanudar, usar el comando con --resume.
